**JwtUtils.java**

**Purpose:**
This class is a central component for handling security in the application using **JSON Web Tokens (JWT)**. It provides a complete, secure, and robust set of utilities for creating, verifying, and managing the lifecycle of tokens used for user authentication and authorization. It follows modern best practices by using secure cookies for token transport.

**Core Concepts Implemented:**

1.  **JWT for Authentication:** Users prove their identity by presenting a valid JWT. This utility creates and verifies these tokens.
2.  **Access Tokens vs. Refresh Tokens:**
    - **Access Token:** A short-lived token that contains user information (like roles/scopes) and is sent with every request to access protected resources.
    - **Refresh Token:** A long-lived token that is used only to obtain a new access token when the old one expires. It does not contain sensitive permission data. This avoids forcing the user to log in again frequently.
3.  **JWS with HMAC:** The tokens are signed using a symmetric key (HMAC with SHA-512), ensuring that they cannot be tampered with by a client or an attacker. This is a JSON Web Signature (JWS).
4.  **Token Revocation (Denylist):** A critical security feature. When a user logs out, their token's unique ID (`jti`) is stored in the `invalidatedTokenRepository`. The `verifyToken` method checks this repository to ensure that a logged-out token cannot be reused.
5.  **Secure Cookie Transport (`httpOnly`, `SameSite=Strict`):**
    - The tokens are not stored in client-side JavaScript (like `localStorage`), but are instead transported in `httpOnly` cookies. This is a major security enhancement that protects against Cross-Site Scripting (XSS) attacks stealing the tokens.
    - `SameSite=Strict` provides strong protection against Cross-Site Request Forgery (CSRF) attacks.

**How it works (Key Methods):**

- **Configuration:**
  - The class is configured via application properties for the secret key (`demo.secret.key`) and the expiration times for access (`demo.time.token.access`) and refresh (`demo.time.token.refresh`) tokens.

- **`generateToken(User user, boolean isRefresh)`:**
  - The main token creation method.
  - If `isRefresh` is `false`, it creates an **access token** with the user's roles/permissions embedded in a `scope` claim (e.g., `"scope": "USER ADMIN"`). This token has a shorter lifespan.
  - If `isRefresh` is `true`, it creates a **refresh token** with a much longer lifespan and *no* scope information.
  - Both tokens are given a unique ID (`jti`), a subject (`sub`), and an expiration time (`exp`).
  - The token is then signed using the secret key and serialized into the standard `header.payload.signature` JWT string format.

- **`verifyToken(String token)`:**
  - The core validation logic.
  - It performs three critical checks:
    1.  **Signature Verification:** It uses the same secret key to verify that the token's signature is valid and the token has not been altered.
    2.  **Expiration Check:** It ensures that the current time is before the token's `exp` claim.
    3.  **Revocation Check:** It checks if the token's ID (`jti`) exists in the `invalidatedTokenRepository`. If it does, the token is rejected.
  - If any of these checks fail, it throws an `UNAUTHENTICATED` exception. Otherwise, it returns the parsed `SignedJWT` object.

- **`generateAccessCookie(String token)` & `generateRefreshCookie(String token)`:**
  - These are factory methods for creating secure `ResponseCookie` objects. They package the generated token strings into cookies with the appropriate security flags (`httpOnly`, `path`, `maxAge`, `sameSite`).

- **`clearToken(HttpServletResponse response)`:**
  - This method handles the client-side part of logout.
  - It creates and sends back two new cookies with the same names as the token cookies but with an empty value and a `maxAge` of 0. This instructs the browser to delete the existing authentication tokens immediately.

**Usage:**
- **Login:** After a user successfully authenticates with a username/password, the application calls `generateToken` twice (once for an access token, once for a refresh token) and uses `generateAccessCookie` and `generateRefreshCookie` to send them to the client.
- **Subsequent Requests:** The browser automatically includes the token cookies with every request. A security filter on the backend extracts the access token, calls `verifyToken` to validate it, and establishes the user's identity for that request.
- **Token Refresh:** When the access token expires, the client makes a specific request to a refresh endpoint. The backend verifies the *refresh token* and, if valid, issues a new access token.
- **Logout:** The application invalidates the token on the server-side (by adding its `jti` to the `invalidatedTokenRepository`) and calls `clearToken` to remove the cookies from the browser.
